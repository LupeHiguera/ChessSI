Keep net12 running and identify the trainer's peak allocation before rewriting its storage. The current trainer already packs boards into 24 bytes and expands them on the GPU. The proposed +84 Elo threshold for deeper labels extrapolates from a confounded data expansion and should not decide which experiment is allowed. ## Packing already exists

The trainer stores an 8-byte occupancy mask and 16 bytes of piece codes, then reconstructs the feature lists per GPU batch. Host mode also already places targets, indices and epoch permutations on the CPU. The proposed change to packed boards plus GPU decoding is therefore present at this source. A claimed additional 2.5-fold capacity improvement needs a different mechanism. [Representation](https://github.com/LupeHiguera/ChessSI/blob/98f21e5acbbd7e5832a098c501ca7d2df3e30a53/nnue/train.py#L82), [host mode and decoding](https://github.com/LupeHiguera/ChessSI/blob/98f21e5acbbd7e5832a098c501ca7d2df3e30a53/nnue/train.py#L463).

Let R be raw rows, U retained unique rows, T training rows, and F rows in one source file. For host mode with the ordinary auxiliary head and no policy or teacher head, source-derived array accounting is:

| Phase | Array storage |
| --- | --- |
| Loader output | 38U bytes |
| Training before epoch order | 38U |
| During an epoch | 38U + 4T |
| Replacing the epoch order | Up to 38U + 12T |
| Constructing targets while old arrays remain | Approximately 51U |

The training resident term comprises 24 bytes of board, one Boolean side-to-move byte, eight target bytes, one retained validation flag and four bytes of train/validation indices per unique row. The epoch transition can temporarily retain the old order, the new permutation and the newly indexed order. CPU tensors made with torch.from_numpy share the NumPy allocation; counting both objects as separate storage would inflate the estimate. [Source](https://github.com/LupeHiguera/ChessSI/blob/98f21e5acbbd7e5832a098c501ca7d2df3e30a53/nnue/train.py#L457), [PyTorch semantics](https://docs.pytorch.org/docs/2.14/generated/torch.from_numpy.html).

At U = 500M and T = 0.98U, those expressions give 20.96 GB during an epoch, 24.88 GB during order replacement, and 25.50 GB during target construction. These are decimal GB of identified arrays, not measured process memory or a safe machine capacity. Allocator retention, runtime allocations, file cache and loading peaks remain additional costs.

Claude reports net12 loading took 3,874 seconds from freshly parsed inputs, with VmHWM 26.24 GB and training RSS 19.53 GB. An earlier 560.6M-raw-row attempt was OOM-killed while parsing a whole file of about 329M lines; the current input splits the large sources into roughly 20M-line pieces. This supports measuring loading phases first. Net11's reported 35.4 GB peak involved more retained rows and cached input, so the two peaks do not isolate a loader improvement. Extrapolated capacities such as 670M or 900M rows remain conditional on the input layout, cache path and memory limit, rather than safe guarantees. [Operator measurements](https://github.com/LupeHiguera/ChessSI/issues/21#issuecomment-6435397775).

Cut alignment in the active input pieces is unverified. If a cut divides a game, per_file treats the next piece as a new group, potentially placing fragments in different train/validation partitions. At horizon four, at most four preceding raw auxiliary targets per artificial cut change to outcome fallback; main search/result labels remain unchanged if row order is preserved. This is a boundary caveat, not evidence that net12's corpus is invalid or its run should stop. Future storage sharding should preserve original groups and future labels. [Grouping and targets](https://github.com/LupeHiguera/ChessSI/blob/98f21e5acbbd7e5832a098c501ca7d2df3e30a53/nnue/train.py#L207).

Loading can dominate training. Raw metadata totals 26R bytes. One deduplication phase keeps first-index fragments and their concatenation, contributing 16U more bytes, before other workspace. The previously reported 63-bit-key partition issue remains: default eight-way partitioning uses a 64-bit shift even though only 63 bits are populated, leaving four nonempty ranges.

During the frozen feature pass, load_file retains cached feature chunks and concatenates the whole source file. Each representation uses 64F bytes, so their coexistence contributes 128F. With P unique boards already packed, a useful touched-array estimate is 18U + 24P + 128F, plus the last source file's retained future-target array and other workspace. Once concatenation returns, the feature term drops to 64F and encoding adds bounded temporaries. The packed allocation is filled progressively, so its allocation size is not immediately resident memory. Uncached loading also reads and decodes an entire appended text tail. [Loading code](https://github.com/LupeHiguera/ChessSI/blob/98f21e5acbbd7e5832a098c501ca7d2df3e30a53/nnue/train.py#L171).

Choose the remedy from the dominant phase. Releasing obsolete arrays or correcting partitioning is smaller than changing the training loop. If whole-file feature copies dominate, iterating existing cache chunks can preserve training semantics. Standalone packed NPY arrays can support mapping; adding mmap_mode to existing NPZ archive loads does not map their members. Random mapped access may become limited by storage throughput, while a bounded shuffle buffer deliberately changes data order. [NumPy implementation](https://github.com/numpy/numpy/blob/v2.5.0/numpy/lib/_npyio_impl.py), [mapping documentation](https://numpy.org/doc/stable/reference/generated/numpy.load.html).

A future bounded loader check can use at most 2M frozen rows, 4 GiB and 15 minutes on an assigned core or PC2. Record phase memory and shared allocation identities, then compare retained rows, labels, groups and order exactly. PC2 needs no GPU for loading/packing checks; current full training requires CUDA. Preserve original game grouping and future labels before storage sharding: splitting text into artificial files changes per_file's boundaries, fallback targets and game keys. Keep CUDA target arithmetic for later exact training comparisons. A deliberate shuffle change requires its own quality comparison.

## What net12 can establish

Claude supplied the active manifest during this review. Net12 uses the trainer at fa027d2, reported identical to 98f21e5, with hidden size 256, 20 epochs, seed 1, auxiliary weight 1, future horizon 4 and host data mode. It runs on the 5060 Ti under MemoryMax=40G. Its 505,624,946 raw generation-8 lines retain 436,375,660 unique positions from 5,018,027 game groups: 427,655,324 training and 8,720,336 validation rows. Net11 used 537,588,875 unique positions from mixed generations. Net12 therefore has 81.17% of net11's unique volume. At the default batch size 16,384, completing 20 epochs entails 8,553,106,480 training presentations and 522,060 optimizer updates. These are planned totals derived from the reported counts, not a claim that training has completed. [Active manifest](https://github.com/LupeHiguera/ChessSI/issues/21#issuecomment-6435397775), [net11 record](https://github.com/LupeHiguera/ChessSI/blob/98f21e5acbbd7e5832a098c501ca7d2df3e30a53/nets/README.md#L10).

A net12 win would show that this recent-only recipe can replace net11 under the current resource limit. Teacher network, visited positions, outcomes, auxiliary labels, deduplication winners and training volume all change. Neither a win nor a loss isolates recency. A statistically inconclusive match is not evidence of equal strength; a sufficiently precise, predeclared noninferiority result could support maintained strength with fewer rows. It still would not establish that repeatedly discarding older generations preserves rare coverage.

If that retention decision remains unresolved, a proposed smaller comparison uses 32M unique training rows per arm, with holdouts excluded: A takes generation 8 only; B retains 24M of the same generation-8 rows and adds 8M generation-7 rows. Freeze the 25% replay fraction before outcomes. Hold random initialization, trainer, batch size, epochs and update count constant. At 20 epochs, one seed across both arms costs 1.28B position presentations, so budget this explicitly after the current jobs, not as a free check.

Use the same untouched recent-game panel for both models and an older-cohort guardrail. The current groups are inferred from ply/result changes, not explicit game IDs. Preserve complete conservative groups within verified writer streams, disclose possible merged games, and preserve future targets before sampling. Freeze duplicate precedence and check holdout keys against both training manifests. Validation losses printed on different generation mixtures are not directly comparable. Select practical MSE tolerances and game-grouped uncertainty before training; advance only on a reproducible recent-cohort improvement without a material historical regression. A successful screen earns a second seed, then a comparison trained at the same memory-scale budget, followed by CPU SPRT. A 32M-row result alone does not establish the best retention policy at 500M rows. Failure parks that particular mixture, not every replay policy.

The current trainer initializes a fresh network and Adam. Warm-starting net11, or adding a teacher head, would be additional interventions. Replay capacity and learning updates per collected sample are separate variables in the research literature; its empirical findings provide no ChessSI Elo conversion. [Trainer initialization](https://github.com/LupeHiguera/ChessSI/blob/98f21e5acbbd7e5832a098c501ca7d2df3e30a53/nnue/train.py#L503), [Fedus et al.](https://proceedings.mlr.press/v119/fedus20a.html).

## Depth needs the actual alternative cost

The proposed 1.66X rule uses X = 50.7 and log(4)/log(537.589/233.675), giving about 84.4 Elo. It assumes a transferable log-linear response to distinct data, fourfold end-to-end labeling cost, and comparable teachers and training regimes. Net10 to net11 changed the data mix and increased optimizer steps roughly 2.3-fold at the same 20 epochs. Its gain does not identify a volume-only slope.

Even retaining that model as a sensitivity calculation, its quantity term is X times log(N_shallow/N_deep) divided by log(537.589/233.675), using the unique populations actually available under memory and compute constraints. If both arms fill the same resident capacity, the quantity term is zero; refresh quality, coverage and training cost still matter. If the experiment instead compares 100M deep with 400M shallow, both fit a reported 580M limit, so the quantity tradeoff remains.

Measure labeling and training time separately, and report unique rows, presentations and optimizer updates. Same-row depth comparisons measure quality per row. Equal-budget comparisons answer allocation. Neither the old 84-Elo extrapolation nor RAM saturation alone settles whether deeper labels are worthwhile. Resolve usable training capacity before a large rescore.

## Pin the GPU teacher separately from CPU main

The default-value drift was fixed in PR42. CPU main has since gained SEE pruning, correction history, depth/age replacement and losing-capture ordering. At this pinned snapshot, the GPU still has always-replace TT stores, raw static evaluation, no corresponding main-search SEE gate, and the older capture order. [GPU TT](https://github.com/LupeHiguera/ChessSI/blob/98f21e5acbbd7e5832a098c501ca7d2df3e30a53/gpu/datagen.cu#L576), [GPU move loop](https://github.com/LupeHiguera/ChessSI/blob/98f21e5acbbd7e5832a098c501ca7d2df3e30a53/gpu/datagen.cu#L835), [CPU additions](https://github.com/LupeHiguera/ChessSI/blob/98f21e5acbbd7e5832a098c501ca7d2df3e30a53/src/search.cpp#L120).

A frozen earlier ChessSI search with net11 remains an own-engine teacher. Its data need not be discarded. Record both network and search revisions; an earlier parity test is not a parity test against today's main. GPU network screens likewise use that kernel's search, with CPU timed SPRT retaining the final decision. This extends Claude's existing warning that CPU search branches require a GPU port before GPU screening.
