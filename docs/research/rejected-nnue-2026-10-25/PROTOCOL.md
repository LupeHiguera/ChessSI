# Rejected-move NNUE update audit

Frozen before measurement on 2026-10-25. Owner: GPT-6 (Codex); source review: GPT-6 agents. Main: `35cb09b31fc1efae63e13c1da17a9285623e1cb5`.

## Question

How much accumulator arithmetic is spent on pseudo-legal moves immediately rejected for king safety? This is a Known technique: Stockfish checks legality before its move/update path. This audit is not an implementation trial or a claim of a new algorithm.

In ChessSI `Position::do_move`, the accumulator is currently updated before king safety is checked. A future candidate could reserve the child accumulator slot on all moves, but only apply the delta for legal moves. The reserve remains necessary because every attempted move is undone. Caller review must establish that no failed move is evaluated or searched before undo.

## Frozen procedure

- Keep repository engine sources unchanged. Copy source and Makefile to an ignored subdirectory, adding counters only to the copy. All accumulator work and the final legality result remain unchanged.
- Pin builds to CPUs 14-19, at most six compiler jobs. Pin measurement processes to CPU 19. Threads 1, Hash 16, embedded net10-h256, default optimized build flags.
- Record attempted/legal/rejected moves by parent-in-check and move type, plus the number of add/sub feature-row operations times both perspectives and hidden width. This is an arithmetic count, not elapsed time or memory traffic.
- Run the unchanged 14-position bench at depths 7 and 11. Run one 16-game self-play sample with seed 20261025, 5,000 requested nodes and eight random opening plies. Keep CPU datagen's normal adjudication. All data is generated by ChessSI.
- Both binaries must pass `make test`; bench node counts must match at each depth (depth 7 must be 158506). Self-play output must match byte for byte, including search scores, results and static eval. All attempts are logged, even if a check fails.
- Record source/network/script hashes, build commands, compiler, CPU affinity, counters and output hashes. No GPU work. No comparison of instrumented timing with baseline timing: the counters add overhead.
- Hard runtime bounds: 120 seconds per bench, 600 seconds per 16-game datagen run, 180 seconds per build/test command. Stop and report a bound exceeded rather than widening this sample.

## Interpretation fixed before results

Below 1% rejected accumulator updates in both the deeper bench and datagen: park this narrow candidate. At least 5% in either workload: justify a later small implementation and timing trial, provided the caller audit passes. Between these thresholds: inconclusive, low priority. These are engineering screening thresholds, not statistical tests or Elo predictors.

Even eliminating a large fraction of accumulator calls may save little total runtime: evaluation, move generation, search, branch costs and TT prefetch latency remain. The corpus is small and bench-biased. No strength claim, accepted engine change, or SPRT follows from this audit alone.

## Follow-on experiment, if justified

Separate implementation branch, unchanged NNUE/network, legal child accumulator equal to full refresh, rejected child immediately undone, null moves unchanged, and stress of captures, promotion, en passant and castling. Require unchanged single-thread fixed-depth nodes/scores/PV and alternating fixed-work timing on the assigned cores before spending SPRT games. Do not combine an adjacent network-reload issue with this optimization.
